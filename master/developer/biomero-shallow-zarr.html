Working with shallow OME-Zarr results

BIOMERO stores a workflow result as retained data plus references to its known managed input. The result remains a distinct OMERO Image or Plate with its own provenance. Storage is saved on the shared filesystem, without deleting the source or suppressing result registration.

On disk: shallow off versus on

Example: one 2D v2 Image, unchanged intensities, one new cells label. The directory contents below represent the same analysis result. The two comparisons use grey borders for Shallow OFF and purple for Shallow ON. Here, fills describe contents: blue pixels, green labels, yellow reference/provenance metadata.

The blue folders disappear from the result: full-resolution image chunks and their pyramid arrays. The original source retains those pixels. Green is added by the workflow, not by the shallower: those label files remain in both result formats. Two small JSON files are added; .zattrs loses multiscales and gains a biomero pointer to the shallow manifest. These edits affect the returned image metadata; the source is unchanged by shallowing. Other output files, such as CSV measurements, remain.

The file 0.0 is an example pixel chunk; … stands for further chunk files. Blank rows on the right align the retained labels; they are not files. This is a file-layout example, not a file-count or size scale. 0, 1, … are example array names; s0, s1, … work too. A Plate repeats the image layout under its well/field paths. V3 uses zarr.json in place of the v2 metadata files; the same keep/omit/reference distinction applies.

The importer creates a new result Image or Plate in both cases. With shallow storage on, it registers the source pixel path for primary intensities and adds a biomero.zarr.shallow MapAnnotation locating the shallow result and its references. The viewer and later transfers use that result reference to find labels and reconstruct the collection.

PixelBuffer does not need to interpret the shallow manifest: it reads the source path already registered by the importer. Label-backed mask Images and the optional Plate preview similarly register their retained label paths. Preview controls.

The two JSON files have separate jobs:

File

Purpose

.biomero-shallow.json

Image/label nodes, omitted arrays, source storage bindings and decision basis; measured identities when comparison was used

.biomero-shallow-report.json

Decision, input snapshot and tool provenance; remote receipts bind this report to the expected helper run

Source indexing is separate: canonical-source annotations (biomero.zarr.source / biomero.zarr.plate-source) record the reusable input. Indexing can also add a .biomero-canonical.json marker to the source store; this is metadata, not another pixel copy. Keep the source, retained labels and their references together in retention and backup policy. The shallow folder alone is incomplete.

Workflow input: reuse, reconstruct or export

The workflow receives full input in its requested format. It does not resolve BIOMERO shallow references itself.

Reconstruction assembles a temporary full Zarr from the source and all retained/referenced labels. Export reads the selected OMERO pixel view; it does not reconstruct the shallow result’s full label collection. A format mismatch uses export and leaves the original canonical registration unchanged.

What registering or promoting a canonical Zarr entails

A canonical Zarr is the stable managed source bound to a workflow input. Its locator, generation and image semantics can be recorded without hashing original pixels. Comparison fingerprints are calculated only when needed; source-linked handling does not require an otherwise unused fingerprint. Yellow steps below mark pixel reads.

Pixel calculation

What canonical registration changes

Existing authoritative backing Zarr

Original-image hashing is deferred until comparison needs it; labels retain their separate policy

Records source binding and semantics in place; no new pixel copy

Eligible fresh OMERO export

Full-resolution source/export verification remains a separate promotion check

Commits the verified export to stable managed canonical storage and attaches source records

Current comparison fingerprint already cached

Reuses that fingerprint for the same source generation and compatible resolution

Records the workflow input snapshot; no repeated source hash

Old or missing comparison profile

Local importer reads the same authoritative backing Zarr when comparison is needed

Replaces the cached record with the current profile; no export, copy or reimport

Only the matching generation is reused. A temporary format-mismatch export or TIFF conversion input is not promoted. Failed indexing/promotion leaves the full workflow input usable without deduplication for that selection. Missing dependencies of a shallow input must be resolved before it can be reconstructed. Old records are detected as stale, never relabelled as current fingerprints. There is one current cache rather than parallel legacy and pyramid identities. The remote helper uses current cached fingerprints; it cannot refresh them from the authoritative managed store. Missing/stale fingerprints keep the remote result full so the importer can compare and cache from the actual source. Post-analysis HPC input copies are not authoritative comparison sources.

Output handling and comparison

The decision order is:

Condition

Handling

Shallow storage disabled

Full results, without deduplication-only hashing or pruning

Enabled, usable run-bound RO-Crate label output declaration

Automatically use the known input as image background; no original-pixel comparison or admin approval

No usable declaration, workflow setting enabled

Use the same source-linked route under the recorded workflow policy

Neither

Compare compatible stored pyramid pixels; unsupported or unmatched results stay full

The administrator setting is [UI] original_pixels_not_required_workflows; see the admin controls. It is independent of automatic RO-Crate handling and input-format selection. No Bilayers output-preservation preset is inferred.

Supported declarations connect the run’s input and label-level result with the output parameter’s exampleOfWork and the crate’s hasPart. The execution record supplies the managed source binding. A root-level Zarr pointer alone does not identify which image arrays are derived. Cheap format, layout and semantic guards still apply; missing or ambiguous evidence falls through to the setting or comparison. The supported result includes the enclosing image and label datasets; bare labels-only materialization is not implemented. Additional derived stores and sidecars are retained.

The original RO-Crate is retained. If its graph explicitly inventories an array or label subtree that shallowing would remove, the artifact stays full rather than leaving stale file claims or rewriting an arbitrary graph. For supported label-output declarations, the retained crate describes the produced labels and the committed shallow manifest records the managed-source relationships.

Each binding records whether it used ro-crate-output, workflow-setting or pixel-comparison. Source-linked decisions do not invent a pixel fingerprint or claim that returned original pixels were measured.

Responsibility

Implementation

Pixel traversal and codes

ISCC-BIO generate_biocode(planes); decoded numerical planes from a stored level, without the high-level file/store checksum

Comparison policy

BIOMERO selects the coarsest compatible stored image level, retains all C/Z/T coverage and checks full-image and selected-level semantics; labels use full resolution

Equality decision

Matching current profiles, code lengths, Instance-Codes and semantic guards; dataset path spelling is provenance, not an equality key

Storage, transactions and references

BIOMERO.shallower; shared contracts from biomero-schema

HPC orchestration and OMERO registration

BIOMERO core/scripts and BIOMERO.importer, respectively

The pixel API’s composite ISCC-SUM and similarity-oriented Data-Code are recorded but do not authorize removal. No raw file-tree checksum or rendered thumbnail is calculated. Numerical planes follow IMAGEWALK Z → C → T traversal with upstream canonical pixel encoding. A single-level image uses full resolution; compatible stored levels require matching dimensions, dtype, axes and transformations without omitting channels, Z slices or timepoints.

Selected-level byte equality is exact. Inferring unchanged full-resolution pixels from a smaller pyramid is BIOMERO’s deduplication approximation, not a full-resolution equality proof or perceptual ISCC matching. Workflows must return internally consistent pyramids. The shared comparison contract defines profile fields, code lengths, reproducibility versions and scientific scope; it is the canonical algorithm reference.

Pruning uses same-filesystem moves and a rollback journal before committing the manifest. Source pixels remain untouched. See configuration and recovery.

Reconstructing a standalone result

The reconstruction recipe creates a self-contained Image or Plate at a new destination, using its referenced source and retained labels. It preserves v2/v3 format and leaves OMERO registrations unchanged. Keep all referenced stores available and allow enough disk space for the full copy.
