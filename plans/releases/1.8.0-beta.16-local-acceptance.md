Two Python processes inside the worker container, each with its own
`SlurmClient.from_config`, called the publication path
`SlurmClient._publish_job_script` (the function `update_slurm_scripts` uses for
each generated script) on the same 148035-byte script, on a start barrier,

| Case | Result |
| --- | --- |
| 15 rounds x 2 processes (30 concurrent publications) | 30 ok, 0 failures |
| 20 rounds x 2 processes, script pre-set to mode 0750 | 40 ok, 0 failures; afterwards mode `750`, 148035 bytes, sha256 equal to the source (`e9725eb32608...`) |
| Staging files left (`find /data/my-scratch -name '*biomero-partial*'`) | none, after every case and at the end of the whole run |
| Control: same two processes with the old shared name (`atomic_put` with the default `.biomero-partial`) | 20 of 40 publications failed with `FileNotFoundError(2, 'No such file')` |

The control shows the harness does hit the race; the b30 path does not.

Observation on the "mode 0750" expectation: the code does not set a mode.
`atomic_put` keeps the permission bits of an existing remote file, and a new
file gets the umask mode. A script that did not exist before is `0644`; after
the workflows the generated `jobs/bilayerstest.sh` and `jobs/stardist.sh` were
`0644` here. The 0750 case above holds because the file was already 0750. If
the checklist means "0750 even for a new file", that is not the behaviour (the
rule is the same in b29).

Verdict: **E and D pass; C passes; A and B fail** on what the beta.15/16 notes
promise for NODE_FAIL: the requeue follow-up of core #131 is not reached by the
batched/detached workflow loop of the scripts. Details below.

### A. Node failure, requeued by Slurm: Fail

Two runs, node taken down while the analysis job RUNNING, resumed 5 s later.
Slurm requeued the job under the same ID (job 40 in a 4-image child, job 42
in a one-image child): `Requeue=1 Restarts=1`, `sacct --duplicates` shows the
same ID as `NODE_FAIL` and then `COMPLETED`, no second job was submitted. The
workflow never saw NODE_FAIL (the next poll already showed PENDING), so the log
has no "was requeued after NODE_FAIL" line, and the workflow did not end DONE:

- Result retrieval waited the full 20 attempts on "Output directory empty on
  SLURM" and the child ended FAILED at 90% (roots `8897c4d0`, `11f99cb8`).
  Cause (verified): the requeued job appends to the same Slurm log, so
  `omero-<id>.log` holds the `Running bilayers_test Job w/ ...` line twice;
  `SlurmClient._LOGFILE_DATA_CMD` (`perl ... and print$1`) prints one match per
  line without a newline, so the data location comes back doubled
  (`/data/.../biomero_X/data/my-scratch/data/biomero_X/data/out`, not an
  existing directory). The job itself wrote its output correctly
  (`data/out/in/*.tif`, "Job completed successfully"). Control with the same
  wrapper and no node failure: root `54b778cb` DONE.

### B. Node failure, requeue disabled (`scontrol update jobid=47 requeue=0`): Fail on the expected behaviour

The job went `NODE_FAIL` and the workflow ended FAILED two seconds later, with
the old text `Oops! State of job 47 is unknown: NODE_FAIL. Stop tracking.` There
was no 10 s re-check and no "ended in NODE_FAIL and was not requeued" line.
Reason: `find_requeued_job_state` and `_follow_requeue` are wired only into
`SlurmJob._poll_state` (`wait_for_completion`). The scripts' loop in
`SLURM_Run_Workflow.py` (about line 2454) calls `check_job_status` directly and
treats `NODE_FAIL` as an unknown state.

### C. Cancel during the requeue window: Pass, with a related finding

- First run (root `fba19828`): the node stayed down for 8 s, the workflow
  saw NODE_FAIL and ended FAILED at once ("Oops! ... NODE_FAIL"), while Slurm
  had requeued job 50 (PENDING, `BeginTime`, eligible about 2 minutes later).
  The cancel script then answered "already finished; nothing to cancel" and
  job 50 stayed queued: an orphaned requeued job (I cancelled it by id).
- Second run (root `a293e9b6`, node down 1 s): the workflow survived
  (JOB_PENDING), job 52 requeued (PENDING). `SLURM Cancel Workflow` then
  cancelled job 52 (`scontrol show job 52`: CANCELLED), the decoy job 48 stayed

  reason ("Parent a293e9b6 cancelled").
