## Candidate and evidence scope

Branch `release/1.8.0-beta.15` at `af3f4c961`, built and run with
`docker-compose.yml`, the release Dockerfiles and the `.env` pins: core 2.9.0b28,
scripts v2.9.0-beta.28, importer 1.5.0-beta.15, OMERO.biomero 1.7.0b19,
Shallower 0.1.0b11. The stack ran as its own Compose project against a private
copy of NL-BIOMERO-Local-Slurm (two 4-CPU nodes, apptainer upgraded to 1.5.5 in
the nodes because the published `latest` image carries 1.3.6, which lacks the
`--mksquashfs-args` flag that the image-pull script uses). Host ports and SSH
material were private to the test. Only the images needed for the cases were
pulled (bilayers_test, simple-zarr-plate-processor, converter, Shallower helper,
and three CellProfiler workflows); the other 13 pulls were cancelled.

Test controls, all on the disposable test cluster: a wrapper in front of
`singularity run` on both nodes that sleeps 100 seconds, so a workflow's analysis
job stays RUNNING long enough to act on; a second Slurm account (`decoy`) with one
running job; a temporary rename of the four view tables and a termination of the
database sessions (row 12). Workflow: `bilayers_test` v0.0.2 on a TIFF image,
detached mode.

The sweep of `remove_input_markers` ran every time ("Result import is done;
removing input markers from ...") with the `Results_Path` it received, and the
runs where the importer consumed the marker itself (kept-full, locally evaluated) were clean.

helper job 21, `location: remote`) the log says "Removed 0 input marker(s)" while
`<ts>/in/Plate Name 0.zarr/.biomero-input.json` is still there. That workflow writes its
store one level down (`<ts>/in/<store>`), and the sweep clears the subfolder list
after the first level, so it never reaches the store. The sweep documents stores
directly below the result folder; whether that layout also exists in other workflows was
not tested. Not run: the failed-import case (marker kept).
