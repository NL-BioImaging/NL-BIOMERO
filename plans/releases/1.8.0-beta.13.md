### Additional SSH checks

Use isolated test connections/jobs. Never stop a shared SSH service or remove
recovery evidence. Record the actual fault phase and preserve original workflow,
task, allocation and output IDs.

- [ ] **Running allocation continuity, inline and detached:** interrupt SSH while
  the original analysis is RUNNING; restore within the configured window. Resume
  the same allocation, retrieve its result and import once. Verify Slurm accounting
  independently, plus successful OMERO heartbeats and mandatory provenance.
- [ ] **Silent channel opening/safe-read stall:** rerun the private-connection
  reproducer against the published runtime. Record native detection time separately
  from the recovery window. Do not promise a universal deadline for every SSH phase.
- [ ] **Submission response lost after acceptance:** reconcile the original sbatch
  allocation instead of resubmitting; cover analysis and relevant helper/converter
  jobs. Delayed accounting must not cause duplicate work.
- [ ] **Result ZIP interruption:** restart downloads from byte zero, publish only
  complete verified data and never repeat successful analysis or import partial files.
- [ ] **Window exhaustion and zero:** a short positive window deliberately ends the
  attempt in FAILED while preserving IDs/receipts/results. Restoring SSH does not
  resurrect it. Explicit zero retains single-attempt behavior; permanent errors fail
  clearly. Healthy elapsed processing is not itself an outage.
- [ ] **Restart and cancellation:** restart only an isolated detached processor;
  eligible unfinished work resumes from persisted identity without duplicate
  submission/import. Intentional cancellation and terminal attempts remain terminal.

The remaining Paramiko acknowledgement-wait behavior is already reported in
[upstream #319](https://github.com/paramiko/paramiko/issues/319). A wait by itself
is not an extra release blocker or a reason to implement another SSH framework.

### Terminal-event persistence: fixed and locally verified

The earlier ACC administrative cancellation inconsistency was initially a scoped
follow-up. Local acceptance has now demonstrated ordinary lifecycle impact:

1. A detached fixture workflow failed before allocation because its private script
   repository was configured without Init. Independent PostgreSQL and native reads
   showed source versions 0–3, while the projection recorded FAILED after handling
   a version-4 WorkflowFailed event. No allocation existed at that point.
2. Normal Slurm Init, with its default analytics rebuild enabled, was then run.
   The detached processor automatically resumed that same workflow and started an
   allocation. No operator replay, repair or resubmission of that UUID occurred.

This violated the requirement that a terminal attempt remain terminal and blocked
promotion of the earlier candidate.
[Core #66](https://github.com/NL-BioImaging/biomero/pull/66) fixes three
inline-listener cache-miss reads that closed a borrowed shared SQLAlchemy session
while the producer event was still pending, cold task status hydration and the
first-event boundary during rebuild. Fourteen focused SQLite/PostgreSQL cases
and configured CI pass. Core `2.9.0b23` is published; its package and converter
image are verified. The beta.23 assembly passed the lifecycle gate below; the table identifies
the final beta.24 companions. Do not classify
this as an upstream library defect.

The corrected candidate passed the live T01 gate: a fresh detached workflow
exhausted a three-second recovery window while its allocation was RUNNING.
Independent reads found exactly one durable WorkflowFailed and a matching FAILED
projection. After native Processor-0 stop/start and normal Init/default analytics
rebuild, the source history and FAILED state were unchanged. Slurm accounting
contained only the original allocation; no import or automatic resumption occurred.
This tests the processor restart path, not plain Docker container restart.

The fix cannot reconstruct previously lost events. Before rebuilding an existing
analytics store, compare terminal projections with persisted source histories.
If inconsistent, preserve the database and evidence and hold detached execution
for operator review. Do not automatically repair or replay those records.

Preserve the original evidence without repairing/replaying the failed workflow
or ACC's two earlier terminal records. Use new isolated fixtures for the fix's
independent source/projection and lifecycle checks. Previously passing SSH and
pixel cases remain evidence for their tested version, not acceptance of the
final candidate on their own.

### Labels-only import preparation: fixed and locally verified

The shallow-OFF native-v3 Image check found another metadata problem after the
SSH/lifecycle gates passed. Scripts rename a native label directory to add a
`.zarr` suffix, but the v3 `attributes.ome.labels` entry retains its old name.
RO-Crate Dataset references can also dangle after this rename, including on v2.
Pixels and mandatory provenance are correct; the returned metadata is inconsistent.

The focused scripts fix [#75](https://github.com/NL-BioImaging/biomero-scripts/pull/75)
preserves existing label paths and removes the rename; regression coverage is in
[#74](https://github.com/NL-BioImaging/biomero-scripts/pull/74).
The published importer already routes these nested paths through its Zarr import
path. This avoids a metadata-rewrite framework and does not add bare-label-only
storage support. Core/scripts beta.24 and admin beta.18 are now published and verified.
Fresh final v2/v3 label imports and clean workflows pass; the final report
records valid native NGFF and adjacent RO-Crate paths alongside pixels/provenance.
